# ADR 058：通过 7998 增量同步 Manager 控制事件

## 状态

已接受。

## 背景

每台服务器的任务执行队列和服务数据库仍然是本机数据。页面查询时逐个访问所有
服务器会产生 fan-out 延迟，也无法可靠处理远端暂时离线。直接复制 SQLite 文件会
把 WAL、并发写入和节点恢复问题带入控制面。

## 决策

1. 每个 Manager 的 `job-index.sqlite` 增加本机拥有的控制事件流、运行路由表和远端
   同步游标。它是本地投影和 outbox，不是跨服务器共享的 SQLite 文件。
2. 任务事件使用 `server_id:sequence` 作为幂等事件号。事件携带任务的提交服务器、
   执行服务器和执行端口；接收方重复收到事件时只保留一次，不重新发射事件。
3. Manager 只向已经登记的对端拉取与自身相关的事件：提交方或执行方是本机的任务
   才进入该对端的 audience。普通任务列表优先读取本地投影；只有首次启动且投影
   为空时才允许一次受控 fan-out 作为兼容引导。
4. 增量同步接口为 `POST /api/federation/sync/events`，手动同步接口为
   `POST /api/federation/sync`。二者都复用现有 7998 Manager 控制面，并使用现有
   Manager proxy token；不新增监听端口。
5. `7997` 继续只负责源码/生成物等大文件数据面。控制事件只传递小型 JSON 元数据，
   不通过 7997，也不通过 8000、7999 或测试服务端口。
6. 当前阶段只同步任务控制投影和运行位置。用户、Profile、源码内容、跨服务器配额
   的权威数据库和内容寻址存储仍按后续控制数据库迁移单独实现。

## 结果

- 正常列表查询不再依赖所有服务器的同步响应时间。
- 对端离线时本地可以保留最近一次任务状态；游标不前进，恢复后继续增量拉取。
- 任务提交方和执行方都能看到同一任务的服务器身份；无关服务器不会接收该任务事件。
- 7998 只增加复用的 HTTP 请求/后台长周期拉取，不需要额外数据库端口或公共端口。
- 事件表需要后续增加保留、压缩和全量重建策略；当控制数据库迁移到 PostgreSQL
  后，当前事件协议可以由 outbox/逻辑复制实现替换，而不改变任务身份字段。
