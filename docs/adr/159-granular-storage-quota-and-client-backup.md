# ADR-159：细分存储配额、选择性清理与客户端备份

## 状态

部分实施；Issue #430 已提供 Job 附件清单、预览令牌与一次性清理，以及 Swift 客户端的校验备份和附件离线回读。Manager 对已认证用户的 Profile 根目录做有界计量，控制库按存储服务器保存最后一次完整扫描；Job、Profile、报告、上传及活跃 account-domain 元数据统一进入逻辑额度。离线服务器使用有观测时间的最后记录，从未测量的服务器不显示为零。完整 Job 详情离线快照和物理磁盘门槛尚未实施。

## 已核实的现状

- 5 GiB 默认额度现在按 principal 汇总各服务器最后观测到的 Job 附件及 Profile 文件，并计入活跃 account-domain JSON 元数据。现有额度值不自动调高，存量可能因此显示超额；上线不删除数据。报告 Job 特殊小节仍按 Job ID 到存储服务器读取结果；删掉生成物可能使该面板失去详情，Job 摘要仍在。
- CLI 单 Job 全量下载和 Swift“下载全部”都校验大小、哈希并写身份绑定清单；Swift 在服务器清理附件后可从验证过的本地副本展示相应表格、图片和下载。完整 Job 详情仍依赖服务器元数据，尚不能称为完全离线回放。Web 不应声称能访问客户端本地副本。
- Profile 本地扫描以认证 principal 限定目录，不跟随符号链接，并按 inode 避免同一服务器上的硬链接双计；它报告逻辑文件字节和观测时间。扫描超出文件数/时间限制会整体失败，不能将部分结果当作总额。不同服务器的本地扫描不能直接冒充全局用量。
- Job 输出清理的 `quota_released_bytes` 是从活跃清单释放的逻辑字节，`disk_removed_bytes` 是本次成功移除文件的逻辑长度；两者不能互相替代。文件删除失败会返回 `failed_files`，已标记删除的残留文件可由显式重试操作按页清除；磁盘块实际回收还受硬链接、文件系统和快照影响。
- 控制库 `quota_server_usage` 保存每个服务器的 Job 输入/输出最后观测记录；`quota_profile_usage` 保存每个服务器的完整 Profile 分类扫描。Manager 每次上线运行一次本机扫描；打开配额页时也刷新在线服务器的读数。扫描失败保留旧记录，乱序响应不会覆盖较新记录。旧记录纳入逻辑额度，但不声称为实时磁盘占用；从未观测的服务器不显示，不能凭旧快照保证当前物理容量。
- Profile 跨服务器读取复用签名 federation public-data 通道；控制库只保留各分类计数、字节和观测时间，不复制文件。页面顶部一个按全部已计量类别合计的占用条，超额时仍展示每一类的占比，并显示真实超额百分比；下方一张类别表。最近一次记录的时间可在分类标签查看，不单列离线服务器警告。
- 现有业务接口可以逐个删除输出附件，但不能逐个删除输入快照；整 Job 或批量清除会影响回放能力。报告/研究空间没有统一的跨服务器字节索引。
- Manager 的 Job 存储控制入口按存储服务器 ID 定位，不接受业务端口作为存储身份。本机由 Manager 直接访问同一 Job 元数据仓库与附件根目录，因此测试服务停止时仍能读清单或执行经预览确认的清理；跨服务器请求经已签名的 Manager federation proxy 发往目标 Manager 的零端口存储控制分支。离线服务器的最近记录只参与占用汇总，不允许对其执行清理。

## 决策

1. **两个层次的计量。** 用户的逻辑额度按稳定 principal 跨服务器汇总，但保留每个存储服务器的分项和观测时间。Job 输入、Job 输出、Profile 工作区、报告发布副本、上传附件分别列示。离线服务器的旧快照必须标记为过期，不视为零。客户端本地缓存不占服务器额度。若报告位于 Profile 工作区内，不能在逻辑额度里双计同一文件；独立发布副本若占实际额外字节则单列。
2. **统一逻辑额度，保留来源。** Job 附件、Profile 文件和活跃 account-domain 元数据按各自权威来源累加；Profile 内硬链接只计一次，控制库元数据与文件字节分别计入其实际存储。任务接纳和待处理任务的额度检查用统一读数。5 GiB 存量额度不自动调高；超额时禁止新增占用，但保留已有内容，待用户按可清理类别处理或管理员调整额度。最后观测快照不是物理磁盘保护的替代品。
3. **一次性预览清理。** “自动清理”是用户点击后预览并确认的一次性动作，不是定时策略。它清理所有可达存储服务器上已结束 Job 的活跃输出附件；分类清理按“测试任务生成物（数据）/（图片）”两类应用同一条件。类别行的删除清理整类；类别详情 overlay 只按完整 Job 清理生成物，不展示逐附件删除。执行时核对预览的数量、字节数和附件身份令牌，变化则拒绝并要求刷新。输入快照、RunSpec、Job 摘要、基础因子、产品组、报告正文与作者工作区不进入此动作。报告引用的 Job 输出可能使实时结果视图失效，界面必须醒目提示；已复制到报告的静态图片不随 Job 清理。多个服务器需逐服务器执行并显示各自结果，不能把未连通服务器当作已清理。
4. **先备份后清理。** 客户端备份必须包含 Job ID、存储服务器身份、附件名、相对路径、大小、SHA-256 和验证时间。Swift 离线回放只读经过验证、与当前身份和 Job 匹配的本地副本；Web 只显示服务器状态。恢复到服务器是单独显式写入，不由查看自动触发。
5. **物理磁盘保护。** 每个数据服务器对 Job 附件、Profile、报告、上传文件共用卷监控可用字节。以最低保留空闲字节加容量比例设写入保护门槛；拒绝新的大附件写入前预估大小，已接纳的 Job 不静默降级或删除。告警和保护阈值应与用户逻辑额度分开，不得以用户配额替代磁盘保护。

## 分阶段验收

- 第一阶段：Job 分类账、分页附件、Web/CLI 逐项删除与一次性分类/全部可清理输出、预览一致性检查和本地可验证下载清单；分类和总额对账。报告/Profile 及基础元数据进入同一逻辑额度，基础因子与产品组仍受保护且不能在配额页删除。
- 第二阶段：Profile/报告/上传的逐服务器完整扫描、上线一次性刷新及最后观测投影；要求冷/热、删除、离线、乱序响应和扫描失败均不把未知记录当零。
- 第三阶段：Swift 离线详情回放与显式恢复；服务器卷级空间保护与告警。此阶段之前不能宣传 Swift 下载等于可离线回放。
