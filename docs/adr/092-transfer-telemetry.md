# ADR 092：7997/17997 传输指标与本地容灾

## 状态

已接受

## 背景

生成物、提交物、研究附件、本地资源和因子源码都通过同一套 7997/17997 数据面传输。
仅查看传输请求记录无法回答“实际传输了多少字节、当前有多少连接、失败集中在哪个
对象类型”，而 PostgreSQL 不应进入字节传输的关键路径。

## 决策

1. 每个 Manager 在自己的传输 SQLite 中保存 `transfer_telemetry` 最终记录和
   `transfer_active_streams` 活跃流租约。记录包含对象类型、上传/下载方向、local /
   direct-pull / direct-push 模式、client/peer 表面、具体动作、预期字节、实际字节、
   开始/结束时间、耗时、状态和截断后的失败原因。
2. 7997 的本地读写、跨节点 direct-pull/direct-push，以及 17997 的 origin/destination
   流都在真实读写成功后计数；不复制、不把 PostgreSQL 加入数据路径。跨节点一次传输
   在参与的每个 Manager 上各有一条本地观测记录，这是按节点审计实际承担的数据量，
   不是把它们假装成一条全局记录。
3. 活跃连接在 capability 验证通过后登记，按字节或最多 0.5 秒更新一次，并使用
   `process_instance_id` 与 `last_seen_at` 做重启/进程异常后的陈旧租约回收。启动和
   传输请求处理时清理过期票据与旧指标；指标保留 30 天，活跃租约按 30 秒无心跳视为
   失效。
4. `GET /api/transfers/metrics` 只允许安全传输上的超级管理员会话访问，默认返回最近
   24 小时，查询窗口最多 7 天，并按对象类型、方向、模式、表面和动作提供汇总。该
   接口是运维观测接口，不向访客、普通用户或 7997 数据面公开。
5. 浏览器的 `fetch → Blob → 直接保存到文件`、Swift 的流式读取或保存文件，在服务器
   看来都是同一条已授权 HTTP 字节流；Manager 只能可靠报告 7997/17997 的网络流成功
   与实际字节，不能伪造客户端文件系统最终落盘结果。若未来需要客户端落盘指标，应
   由客户端另行上报，并与服务器传输记录分开命名。

## 后果

- 本地 SQLite 或 PostgreSQL 短暂不可用不会改变既有 7997 字节面的职责边界；传输指标
  与传输请求共用 Manager 本地存储。
- direct-pull/direct-push 的中继两端都会显示各自实际承担的字节，便于发现瓶颈、断流
  和不对称流量；汇总时应按 `server_id` 解读，不能跨节点简单相加后称为“唯一文件量”。
- 指标接口没有单独端口，不增加 7997/7998/17997 之外的网络暴露。
