# ADR-013: 模板逐条存储与详情懒加载

## 状态

已采纳。

## 背景

用户模板曾按 `(username, kind, scope_key, ff_alias)` 聚合为一个 JSON blob。模板目录查询因此必须读取并解析同一作用域下的全部快照。单因子模板 overlay 还会在页面初始化、点击入口和 drawer observer 中重复请求，并为默认折叠的模板预先传输和渲染详情。

Windows 上 SQLite 文件打开、文件扫描和重复 I/O 的成本更明显，放大了这一存储粒度问题。

## 决策

- `account_templates` 每行保存一个模板，以用户、模板类型、作用域、因子家族和模板 ID 组成主键。
- 名称、模板内因子 alias、排序和更新时间作为独立列；完整模板保存在该行的 `payload_json`。
- 模板目录查询只选择元数据列，不读取 `payload_json`。
- 模板详情按 ID 单独读取；overlay 首次展开或点击加载时才请求详情，并缓存进行中的 Promise 和结果。
- 页面初始化不预取模板；drawer 单次打开期间合并并发目录请求。
- 首次 schema 初始化把旧 collection blob 一次性迁移为逐条记录，迁移完成后删除旧表，不双写。

## 后果

- 目录加载成本不再随快照体积增长，详情成本只由用户实际展开/加载的模板决定。
- 保存整个模板列表的公共 API 语义保持不变，time、params、global 和 group-settings 调用方无需同时迁移。
- 首次升级会产生一次短暂迁移写入；真实数据库副本中 26 个集合、50 条模板约耗时 12 ms。
- 模板 ID 在同一用户、类型和作用域内必须唯一。
