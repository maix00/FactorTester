# ADR-142：研究根对象、研究工作区、报告与证据访问边界

## 状态

已接受；目标架构分阶段实施。

> 本 ADR 中的 Graph/WorkPackage/Graph Branch 与 Graph Evidence 关联约束已被 ADR-156 取代。Research、Report、ReportBranch、Evidence 权限与跨服务器关系继续有效，但必须逐步脱离 Graph schema；Graph 历史数据不迁移保留。

本文记录已经确定的对象关系和访问规则，不把尚未完成的数据库、API、CLI 或页面迁移写成已落地。
当前实现偏离和一次性迁移要求见“当前偏离与实施顺序”。

## 背景

当前研究能力同时存在研究图、Work Package、Profile 报告树、公共报告发布库和 Evidence 目录等几种
容器。报告可以由客户端 Profile 或服务器 Profile Agent 构建，但这些构建来源不应决定报告的业务身份；
报告公开也不应自动等同于其中 Evidence 原始文件可以下载。

需要一个稳定的研究根对象，明确区分：

- 用户拥有的研究及其参与者；
- 某个 Profile 在该研究中的工作区；
- Profile 自己独立的因子工作区；
- 一个研究下的多个报告及其版本来源；
- 可以被多个研究报告引用的 Evidence，以及作为 Evidence 来源的 Job；
- 报告可见性和研究可见性对 Evidence 访问权限的不同影响。

## 决策

### 1. Research 是研究域的根对象

`Research` 是用户名下可持续存在的研究对象，至少包含 `research_id`、`owner_ref`、标题、生命周期和
可见性。一个 Research 可以拥有多个 Report、多个 Research Workspace 和多个 Profile 成员。Evidence
只与 Report 建立直接绑定，Research 通过其 Reports 投影证据集合。

对象关系如下：

```text
Principal
  └── Research
        ├── ResearchMembership ── Profile（一个或多个）
        ├── ResearchWorkspace（每个参与 Profile 可有一个）
        ├── Report（一个或多个）
        ├── Graph / Branch / WorkPackage 投影
        └── Report ── EvidenceLink ── Evidence（Evidence 可被多个 Report 引用）
```

Research 是业务归属和授权边界，不是某个 Profile 的别名，也不是因子工作区的另一种名称。

### 2. 不建立“Research Profile”实体，使用成员关系

一个 Research 可以绑定一个或多个 Profile，一个 Profile 也可以参与多个 Research。绑定关系使用
`ResearchMembership` 表达，并记录参与角色、状态、加入者和时间。

Profile 仍然是独立的身份和 Agent 绑定对象；“本人”只是外部 Profile 列表中的身份标记，不在每个
Research 容器内复制一套特殊逻辑。

服务器 Profile Agent 与客户端 Profile 使用相同的 Research、Membership、Workspace、Report 和 Evidence
协议。服务器端只改变存储根目录和执行位置，不改变对象 schema、权限判断或 CLI 语义。

### 3. Research Workspace 与 Factor Workspace 分离

某个 Profile 处理某个 Research 时，使用该 Research 下、按 Profile 隔离的 `ResearchWorkspace`。它保存
研究过程、报告草稿、图分支、局部分析和引用关系；同一 Research 可同时存在多个 Profile 的工作区。

Profile 的 `Factor Workspace` 是独立的因子库副本/工作树，用于因子家族、因子和因子集合的源码及其
同步，不因参与某个 Research 而改变归属。Research Workspace 不得成为因子库的隐式权威，也不得把
Factor Workspace 合并进 Research Workspace。

现有用于测试作者配置的 `research_workspaces` 表和旧的 Work Package/Branch 结构，不因本 ADR 自动改名或
被运行时重建；它们必须通过后续明确迁移逐步映射到上述语义。

### 4. Report 属于 Research，但不再专属于单个 Profile 或 Workspace

一个 Research 可以有多个 Report。Report 的规范身份由 `research_id` 和 `report_id` 确定；Report 版本
可以记录产生该版本的 `workspace_id`、`profile_ref`、构建来源和时间，作为 provenance，而不是 Report
的唯一所有权或授权边界。

Research Workspace 内的报告创作层级固定为：

```text
Research
  └── ResearchWorkspace（一个参与 Profile）
        └── WorkPackage（一个工作任务范围）
              └── Report（一个稳定 report_id）
                    ├── Branch main
                    ├── Branch experiment-a
                    └── Branch experiment-b
```

一个 Work Package 只能对应一个逻辑 Report。Branch 是该 Report 的分叉版本，保留独立内容、提交历史、
HEAD、来源 Profile 和状态，但不得因为分叉而获得新的 `report_id`。Report 专门阅读页在同一个左栏 Tab
内通过下拉框选择 Branch；每个 Branch 分别保存章节、展开状态和阅读位置。只有用户明确执行“派生为独立
报告”时，才新建 Work Package 和 `report_id`，不得把普通 Branch 自动升级为新 Report。

客户端构建和服务器 Agent 构建继续由 `build_source` / `build_source_ref` 标识。报告发布是 Report 的
公共投影，发布记录保留报告 ID、Research ID、来源 Profile 和发布可见性；发布投影不是另一份 Report
权威数据，也不改变 Report 的 Research 归属。

### 5. Evidence 是跨 Research 可复用的独立对象

Evidence 由其 owner 和稳定的 `evidence_ref` 标识，可以被多个 Report 引用，不为每个引用复制文件或
生成物。Research 本身保持抽象，其证据集合由所属 Reports 的 EvidenceLink 投影得到。EvidenceLink 至少能够表达：

- `evidence_ref`；
- 必填的 `report_id`；`research_id` 只从 Report 归属派生，不作为独立 Evidence 绑定；
- 引用者 Profile、用途和创建时间；
- 关系状态及撤销时间。

`applicability` 是用户对证据适用对象与环境的可修改解释层，不属于 Evidence 的不可变内容身份，也不
参与 `evidence_ref` 哈希。修改 applicability 不得改写 fragment、来源、内容哈希或证据引用。Research
详情可以提供“证据”页，但该页只能去重聚合所属 Reports 的 EvidenceLink，不建立 Research-Evidence
直接关系，并应展示每条 Evidence 来自哪些 Report。

Job 是 Evidence 的一种来源/证据类型；Job 自身及其生成物仍以不可变 Job/Artifact 引用定位，不把一次
Job 结果复制成多份研究文件。

Graph、Branch 和 Research 不各建一套 Evidence 绑定。需要表达研究事实时引用承载该 Evidence 的 Report；
需要回溯 Job 时，从 Evidence source provenance 读取。

Evidence fragment 使用按来源区分的精简清单：共同字段只有来源引用、selector、内容哈希、媒体类型和
长度。Job fragment 只记录 Job ID、权威服务器、冻结身份哈希、selector 与由服务端计算的 fragment 哈希；
不得复制 Job 生成物，也不得接受调用方自行声明的 preview 或 fragment 哈希。服务器已有对象同样只保存
对象引用。只有本地文件或无法从权威来源稳定重建的摘选才创建独立内容对象，并优先保存摘选后的字节而
不是整份文件。

跨服务器只同步 Evidence 与 fragment 清单。查看、下载或分析确实需要内容时，才通过既有对象数据面读取；
接收方只核对 SHA-256、长度和媒体类型，不另建复杂的副本调度协议。

Evidence 的元数据、预览和原始文件必须使用同一套对象权限 helper。表格、报告页面和跨服务器数据面
不得各自实现一套“是否可下载”的判断。

### 6. Report 可见性和 Research 可见性分开

Report 可以独立发布或共享；Research 也可以独立公开或授权给其他用户的 Profile。两者不是同一个开关：

- 两类对象统一使用四级可见性：`private`（仅自己）、`superiors`（当前账户上级链）、
  `authorized`（明确选择的用户）和 `public`（全体用户）；
- `superiors` 必须在访问时根据 Manager 账户树动态解析，不持久化一份容易过期的上级名单；
- 指定用户必须从当前服务器或客户端可见的账户目录搜索选择，持久化稳定的用户标识，不以自由文本用户名
  作为主要交互；
- 两类对象都可以创建一次性或长期分享链接。链接明文只在创建时返回，数据库仅保存摘要；一次性链接由
  首位登录用户领取，长期链接可由多个登录用户领取，所有者可以设置失效时间并在后续管理界面撤销；
- 领取 Report 链接只增加该 Report 的授权，不授予整个 Research 或 Evidence 下载权限；领取 Research
  链接则按 Research 授权规则解析 Evidence 权限。

- Report 可见性决定用户能否看到该 Report 的公开投影；
- Research 可见性决定用户是否成为研究参与者/授权访问者，以及是否获得研究证据的完整下载能力；
- Evidence owner 始终拥有查看、预览、下载和管理权限；
- 仅因 Report 已公开或共享而获得的 Evidence 权限，只能查看 Evidence 元数据和允许的预览，不能下载
  原始文件、生成物或完整 Job 产物；
- Research 对用户公开或授权后，用户可以查看并下载该 Research 所授权 Evidence 的原始文件和生成物，
  但是否可以管理对象仍由 Research 角色和 Evidence owner 决定；
- Research 和 Report 都不可见时，Evidence 不可见。

有效权限由服务端统一解析，至少返回 `can_view`、`can_preview`、`can_download`、`can_manage` 和
`access_basis`（例如 `owner`、`research`、`report`），前端不得根据 `visibility` 自行推断下载权限。

目标访问矩阵如下：

| 访问来源 | 查看 Evidence | 预览 | 下载原始文件/生成物 | 管理 |
| --- | --- | --- | --- | --- |
| Evidence owner | 是 | 是 | 是 | 按 owner 权限 |
| Research owner/授权成员 | 是 | 是 | 是 | 按成员角色 |
| 仅能看到已共享 Report 的用户 | 是（仅关联证据） | 允许的预览 | 否 | 否 |
| 无 Report/Research 访问权的用户 | 否 | 否 | 否 | 否 |

当同一用户同时满足多个条件时，取更强的有效研究授权，但不能因为 Report 发布记录存在就越过 Research
或 Evidence 的 owner/成员规则。匿名公开 Research 的下载权也必须由同一个 helper 授予，而不是由报告
静态资源路由直接放行。

### 7. API、CLI 和页面按 Research 领域组织

目标 canonical 业务入口为：

```text
/api/research/...
factortester research ...
```

该入口负责 Research 的创建、列表、详情、成员、Research Workspace、Report 及 Report-Evidence 关系和
可见性操作。CLI 不要求 Evidence 直接绑定某一个 Profile；Profile 参数只在成员、执行者或工作区语境
需要时出现。

现有 `/api/client/research`、`/api/public-research`、`/api/server-research` 和
`/api/research-evidence` 在迁移期可以分别作为客户端本地投影、公共发布投影、服务器 Agent 传输面和
Evidence 数据面，但它们必须调用同一个 Evidence/Report 访问 helper，并返回稳定的 `evidence_ref` 和
访问能力字段。Evidence 详情不接收“从哪个 Research 访问”的上下文；所属 Research 仅由引用它的
Report 反向投影。上述入口不是第二套 Research 权威，也不得继续各自实现权限或复制目录。

### 8. 研究功能入口以 Research 为中心

“研究”功能入口增加用户自己的 Research 管理页，至少支持 Research 列表、创建/归档、成员、报告和
可见性查看。顶层“证据”页独立管理 Evidence 总目录，Report 内管理其 Evidence 引用。Report 仍可作为独立左栏 Tab 打开；打开后显示其所属 Research 和来源
Workspace/Profile。

研究详情中的 Reports、Profiles、Workspaces、Graph 等内容采用按 Tab 懒加载；研究报告列表是 Research
下的子视图或 Research 分组视图，而不是继续作为唯一根容器。Profile Agent 管理和 Agent 会话仍是
Profile 侧能力，不被塞进 Research 的对象模型。

## 一次性迁移要求

迁移必须是可审计、幂等的显式迁移，不得在请求处理时偷偷补列、复制文件或临时猜测 Research。

对现有每一份客户端报告、服务器 Profile Agent 报告和已有公共发布记录：

1. 创建一个与报告同名的 Research；标题为空时使用报告 ID 作为回退名称。
2. 将原 Report 关联到该 Research，保留原 `report_id`、发布 ID、owner、构建来源、Profile provenance、
   报告版本和既有可见性；不复制报告正文、附件或生成物字节。
3. 将能够解析的 `evidence_refs`、Job/Artifact 引用回填为 EvidenceLink；无法解析的引用保留为待处理
   状态，不因迁移而删除或伪造 Evidence。
4. 把原始构建 Profile 作为 ResearchMembership 的初始成员；服务器 Agent 与客户端报告使用同一规则。
5. 已经完成迁移的来源再次执行时不得创建第二个 Research；失败项可以单独重试并留下迁移记录。
6. 迁移完成后，新的 Report 必须要求 `research_id`；新代码不得继续创建没有 Research 归属的孤立报告。
7. 同一历史 Work Package 内的多个 Branch 必须迁移为一个 Report。若旧实现曾为各 Branch 生成不同
   `report_id`，显式迁移应为该 Work Package 生成一个稳定规范 ID，并把旧 ID 作为来源 provenance 保留；
   不得据此拆成多个 Work Package 或多个同名 Research。

迁移不改变 Profile Factor Workspace 的目录和版本，也不把现有测试作者配置工作区表当作 Research 根对象
直接覆盖。历史研究图、Work Package 和 Branch 应先登记 provenance，再按其实际归属补充 Research/成员/工作区
关系。

## 当前偏离与实施顺序

当前代码已建立 Research 关系模型的权威表：

- `research_catalog_researches`：Research 根对象、生命周期与可见性；
- `research_catalog_memberships`：Research 与 Profile 的成员关系；
- `research_catalog_workspaces`：每个 Research/Profile 组合的 Research Workspace 登记；
- `research_catalog_reports`：Report 对 Research 的规范归属及构建来源；
- `research_catalog_report_evidence_links`：Report 与 Evidence 的直接关系；
- `research_catalog_migrations`：旧报告的显式、幂等迁移记录。

当前 Web 也已提供 Research 根列表、Research 详情、顶层研究报告和 Evidence 目录；
`/api/research/...` 与 `factortester research ...` 已有根对象、成员、Workspace、Report、
EvidenceLink 和显式报告迁移入口。

当前 Evidence 目录、详情、Report 反向引用、Job Artifact 与本地文件对象均使用统一的
Research/Evidence access helper。对象字节通过 7998 授权能力定位 7997 数据面；Report-only
访问只能读取允许的预览，Research 授权用户和 Evidence owner 才能下载原始对象。

仍存在的明确偏离为：

- 少量旧 Research/Evidence 路由仍作为 canonical service 的 Adapter 保留，后续不得继续增加
  平行的权限判断或对象传输实现；
- `research_catalog_workspaces` 已是 Research Workspace 关系权威，但实际工作目录的创建、
  客户端/服务器统一布局与生命周期还没有完全由该记录驱动；
- 报告迁移 service、API 和 CLI 已覆盖 FTClient 本地 Profile、服务器 Profile Agent 和
  公共发布投影；本地 Work Package 身份迁移会留下收据，但生产数据仍须在部署后显式执行并验收；
- 旧 Work Package、Branch、报告树和测试作者 `research_workspaces` 仍作为过渡投影存在，
  保留路由必须逐步收敛为 canonical Research service 的 Adapter；
- Swift 的 Research 入口已与 Web 使用同一组 `researches/evidence/reports/graph/profiles/agent-models`
  语义，并复用嵌入式 Web 研究页面；原生侧仍需随 canonical service 生命周期继续收敛。

实施顺序固定为：

1. 部署后显式执行上述报告身份迁移及 EvidenceLink 回填，完成 FTClient、服务器 Profile Agent
   与公共发布来源的幂等验收；
2. 让 Research Workspace 的实际目录创建和生命周期完全由 `research_catalog_workspaces` 驱动；
3. 将保留的投影/传输路由收敛为 `/api/research/...` 与 `factortester research ...` 的 Adapter，
   禁止新建孤立 Report；
4. 在客户端离线、服务器 Agent、跨用户共享、Report-only 访问、Research-only 访问和 Evidence owner
   访问下做完整回归，确认没有第二套权限链路。

## 不采用的方案

- 不把 Report 继续作为 Research 的根对象；一个研究必须能容纳多个报告。
- 不把某个 Profile 或其 Factor Workspace 当作 Research 的唯一容器。
- 不创建专门的“Research Profile”对象；使用 ResearchMembership。
- 不因为 Report 公开就自动允许 Evidence 原始文件下载。
- 不为每个 Research/Report 复制 Evidence 文件或 Job 生成物。
- 不用运行时迁移补齐旧报告、旧关系或旧数据库字段。

## 后果

正面后果是研究协作、报告发布、证据复用和下载权限可以分别表达；客户端和服务器 Agent 也能共用同一
业务协议。代价是需要一次显式迁移，并需要暂时维护旧报告树、Work Package/Branch 与新 Research 之间的
provenance 映射。未完成迁移前，任何新功能都必须遵守本 ADR 的目标边界，不得继续扩大旧的 Profile-only
或 owner-only 查询链路。

## 验收条件

- 一个 Research 可以有多个 Report 和多个 Profile 成员，每个成员有独立 Research Workspace；
- Profile Factor Workspace 与 Research Workspace 在数据、权限和生命周期上相互独立；
- 现有每份报告都能幂等迁移到同名 Research，原 Report ID、发布记录和来源信息不丢失；
- Evidence 可被多个 Report 引用，Job 只作为来源且不产生重复文件；
- Evidence owner、Research 授权用户、仅 Report 访问用户和无权限用户符合访问矩阵；
- 研究报告、对象传输、客户端投影、服务器 Agent 和 Evidence API 使用同一 access helper；
- “研究”入口能管理用户名下 Research，报告仍能打开独立 Tab，且各内容按需加载；
- 新 API/CLI 不再创建没有 Research 归属的报告，也不增加平行的 Research 目录入口。
