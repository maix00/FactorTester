# ADR-143：策略库与配置内临时策略

## 状态

已接受（2026-09-01）。本文记录已经落地的策略库、回测配置内临时策略和运行时冻结边界。
它不把旧的源码上传数组误写成新的公共策略库；旧字段只作为兼容输入或 Job 读取投影保留。

## 背景

回测原先只有随一次 Run 上传的策略源码。把这类源码直接当成可共享策略会造成三个问题：

- 用户无法区分可复用对象和只属于当前配置的临时对象；
- 修改策略后，历史 Run 可能意外跟随最新源码；
- Web、CLI、服务器 Profile Agent 需要各自实现策略查询和权限判断。

同时，策略的 `target_strategy_id` 是运行域中的组或策略目标标识，不一定是 Python 标识符；只有源码入口类名需要遵守 Python 标识符规则。

## 决策

### 两种作者对象

策略分为两个互不混淆的存储模式：

1. **策略库策略**：由 `/api/strategy-library/strategies` 管理，属于所有者，具有不可变源码版本、可见性和共享授权。
2. **配置内临时策略**：只属于当前 `ResearchConfiguration`，不进入策略库，不具有独立的共享属性；删除配置或解除最后一个绑定后即可清理。

回测配置使用以下 canonical 结构保存配置内策略：

```json
{
  "shared": {
    "temporary_objects": {
      "strategies": [
        {
          "temp_ref": "temporary-strategy:<id>",
          "name": "盘中反转",
          "entrypoint": "IntradayReversal",
          "source_code": "...",
          "source_sha256": "<sha256>",
          "hooks": [],
          "requirements": {}
        }
      ]
    }
  },
  "analyses": {
    "backtest": {
      "strategy_bindings": [
        {
          "binding_id": "strategy-binding:<id>",
          "target_strategy_id": "group-1",
          "source": {"kind": "inline", "temp_ref": "temporary-strategy:<id>"}
        }
      ]
    }
  }
}
```

绑定策略库时，`source.kind` 为 `library`，并固定 `strategy_ref` 与 `revision_ref`；不得只保存策略名，也不得在提交时悄悄跟随当前版本。
同一配置内相同的源码哈希和入口类只保存一份临时源码，可被多个目标绑定。

### 运行冻结和执行边界

提交回测时，Manager 按以下顺序处理策略：

1. 从配置读取 `strategy_bindings`；配置内源码由配置直接提供，策略库绑定按固定版本和当前用户权限读取。
2. 按 `source_sha256` 将每份源码物化为一次 `strategies/frozen/<sha256>.py`，并为每个目标生成一个 source-free 的执行计划。
3. RunSpec 只保存 canonical `strategy_plan`、绑定来源、版本和哈希；不把同一计划再写入 `strategy_specs`。
4. 现有 Job/旧 Worker 需要时可以收到 `strategy_specs` 兼容投影，但该投影不是第二个权威配置，也不改变冻结源码。
5. 执行服务器只使用已冻结的 Run 输入，不在运行中重新查询策略库；重试继续使用原始冻结输入。

源码先经过 AST 校验，入口类必须是原生 `Strategy` 子类；Hook 名称、源码行范围、哈希和字节数由同一检查服务提供。`target_strategy_id` 只做有界的不透明字符串校验，不按 Python 名称校验。

### API、CLI 与文件边界

策略库唯一公共 API 前缀为 `/api/strategy-library/strategies`，包含列表、详情、版本、共享和 CRUD。配置内策略属于测试作者域，使用 `/api/test-authoring/` 下的配置策略资源；策略源码检查继续使用 `/api/run-inputs/strategy/inspect`。

公开 CLI 与领域入口一致：

- `factortester strategy-library ...` 只管理持久策略库；
- `factortester workspace strategy ...` 只管理当前测试配置的临时策略绑定；
- 本地源码检查命令不承担策略库 CRUD，也不能把 `add-inline` 写入策略库。

服务器 Profile Agent 与客户端使用相同 API、CLI、字段和权限语义。内部实现按职责拆分在以下目录，不以文件夹名重新暴露旧接口：

```text
server/services/strategy_library/           # 模型、存储、权限、应用服务
server/services/configuration_strategies.py # 配置内策略结构与校验
server/services/strategy_bindings.py        # 配置到冻结执行输入的编译器
server/manager/http/strategy_library_routes.py
server/manager/web/catalog/strategy-library-*.js
server/manager/web/workbench/strategy-binding-panel.js
tools/cli/commands/strategy_library.py
tools/cli/commands/workspace_strategy.py
```

这些文件保持单一语义职责；新增页面必须复用领域客户端、共享编辑器和源码检查，不再把查询、权限或策略编译复制到页面文件中。

### 页面行为

“策略库”是一级功能入口，列表提供“我的策略”“下级用户策略”“共享策略”三个服务端分页范围。详情页复用对象详情页签，详情表格内展开显示 Hook 源码，源码页显示完整版本源码；编辑只创建新的不可变版本。回测的“自定义策略”是普通内部 tab，选择策略库版本或通过同一编辑器新建配置内临时策略，后者明确显示“只随本次配置保存”。

策略库页面使用路由级懒加载；回测页面只有在打开自定义策略 tab 时才加载策略选择器和编辑器。

## 验收条件

- 策略库 API 和 CLI 可列出、查看、创建、版本化编辑、共享和归档策略，并按用户权限返回操作能力；
- 配置内临时策略不会出现在策略库列表，重复源码只保留一个配置对象；
- library revision 和 inline source 都能编译为唯一冻结源码包，旧版本可重试；
- RunSpec 只有一个 canonical `strategy_plan`，旧 Job 读取仍可通过兼容投影工作；
- Native Strategy 校验、Hook 源码范围和 `source_sha256` 在 HTTP、策略库和回测 overlay 之间语义一致；
- 相关 Web 模块按路由和 tab 懒加载，且策略库文件按领域职责拆分；
- 策略库、配置内策略、执行计划和旧公共路由没有第二个并行权威入口。

## 后果

- 策略库可以安全共享和版本化，历史 Run 不受后续编辑或归档影响；
- 配置内实验策略仍能快速当场创建，不会污染可复用策略库；
- Worker 仍可暂时读取 `strategy_specs` 兼容投影，因此旧执行链不需要一次性重写；
- 后续如果删除该兼容投影，必须先完成 Worker 与 Job retry 的显式迁移和回归，不能直接删除读取路径。
