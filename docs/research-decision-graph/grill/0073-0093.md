# Grill Record: Questions 73–93

Shared code, document, statistical sources, and per-question acceptance
scenarios are indexed in [the evidence registry](evidence-registry.md).

## 73 — Concurrent factor changes

**Question/proposal.** Let Research Agents work on separate Git/research
branches without a global write lock. Use immutable factor version/hash,
structural-hash reuse, sibling variants, and similarity notices.

**User response.** “可以”.

**Resolution.** Planning or later maintenance can consolidate overlap; direct
continuous Research-Agent messaging is not an initial requirement.

**Acceptance.** No overwrite, deterministic lineage, and no duplicate logical
factor for the same structural hash.

## 74 — Obtaining another Agent's raw expression

**Question/proposal.** Server metadata alone cannot reconstruct source. An
authorized Agent imports an immutable FactorRef from the shared local factor
workspace/Git commit; otherwise the server entry remains only a clue.

**User response.** “可以”.

**Resolution.** Import records lineage and never guesses formulas by name.
Source-sync configuration changes transport availability, not identity or
permission semantics.

## 75 — Who chooses the next research batch?

**Question/proposal.** Research completes a Work Package and submits evidence,
failures, possible paths, and gaps. Planning reads the compact workspace index,
recommends priorities, and asks the user to confirm the next primary scope.

**User response.** “可以”.

**Resolution.** Server Maintenance evolves platform capability; it does not
schedule factor-research priorities. Research does not need nested subagents.

## 76 — Compact Research startup

**Question/proposal.** Start with Agent identity/permissions, Work Package,
current graph/node/checkpoint, compact product/data/market summary, candidate
query references, non-whitelist warning, current capabilities/gaps,
workspace/Pyright/backend receipts, and budgets. Exclude full graph, factor
library, catalog, Skill bodies, history, and backend source.

**User response.** Accepted and asked whether checkpoint is local.

**Resolution.** Yes: full research checkpoint is local. Question 77 defines
the server subset.

## 77 — Local versus server checkpoint

**Question/proposal.** Keep full research checkpoint locally and only a compact
coordination checkpoint on the server.

**User response.** “可以”.

**Resolution.** Local state includes source, Provisional Memory, Skill ledger,
and artifact references. Server state includes identity, Work Package, graph,
node, run/job, approvals, hashes, gaps, and budget—not private source or full
reasoning.

## 78 — Checkpoint cadence

**Question/proposal.** Persist on node boundaries, hypothesis freeze, factor
version change, run submission, result audit, capability gap, and before long
tools. Put frequent progress in a local append log and source in Git. Verify
Git/factor/graph/RunSpec hashes on resume.

**User response.** “可以”.

**Resolution.** A mismatch enters recovery diagnosis rather than silent
continuation. Server coordination writes only at low-frequency transitions.

## 79 — Branch-local capability waiting

**Question/proposal.** Pause only the branch needing a missing operator/backend
capability, checkpoint it, create a maintenance gap, continue independent
research, and resume after an exact verified implementation receipt.

**User response.** Accepted, then requested persistent Goal/heartbeat designs
for Server, Planning, and Research Agents.

**Resolution.** Only a Work Package whose every remaining path depends on the
gap becomes fully waiting. Goal continuity was refined in questions 80–90.

## 80 — Persistent goal without persistent LLM

**Question/proposal.** Persist the goal while keeping the Agent offline; a
deterministic watcher/heartbeat wakes it only for changes, timeout, or anomaly.

**User response.** Accepted but said Goal itself is optional; use the most
token-efficient method and, when the runtime is Codex, offer Goal support.

**Resolution.** Persistence semantics are core; provider-specific Goal is an
optional adapter.

## 81 — Runtime-neutral GoalSpec

**Question/proposal.** Use lightweight `GoalSpec + checkpoint + event watcher`
as the source of continuity and optionally synchronize to provider Goal
features. Do not block immediate work if declined or unavailable.

**User response.** “接受”.

**Revision.** The original wording detected “Codex Goal available.” User later
corrected this to detect Codex runtime and attempt/fallback in questions 85–86.

## 82 — Server Maintenance goals

**Question/proposal.** Use a deterministic Standing Monitor for gaps,
anomalies, proposals, version changes, and release failures; create a bounded
Maintenance Case Goal only after an event.

**User response.** “接受”.

**Resolution.** Do not create an endless “maintain everything” LLM goal.

## 83 — Planning goals

**Question/proposal.** Separate the user-owned long-term Workspace Research
Objective from bounded Planning Cycle Goals that produce confirmed Work
Packages.

**User response.** “接受”.

**Resolution.** Deterministic events create a new cycle; Planning does not
poll continuously.

## 84 — Research goals

**Question/proposal.** Bind a Research Goal to one Work Package containing
scope, permissible auxiliary discovery, product/data, graph version,
statistical/backtest acceptance, budgets, stopping, and completion evidence.
States include active and explicit waiting/completed reasons.

**User response.** “接受”.

**Resolution.** Completion means an auditable decision and evidence, not
necessarily a successful factor.

## 85 — Event-first heartbeat

**Question/proposal.** Prefer terminal/release/approval/graph/dependency events;
use adaptive heartbeat only as missed-event/stall fallback. Compare hashes and
deadlines deterministically; coalesce events; no change means no write, message,
or token.

**User response.** Accepted and corrected detection semantics: detect Codex,
not “Codex Goal,” because an Agent may not know Goal availability in advance.

**Impact.** Question 86 formalized attempt-and-fallback.

## 86 — Detect Codex, attempt Goal, fall back

**Question/proposal.** When runtime identity says Codex, prompt once, attempt to
enable/synchronize Goal, and fall back to lightweight GoalSpec if unsupported
or declined.

**User response.** “接受”.

**Resolution.** Core remains provider-neutral and work begins seamlessly in all
cases.

## 87 — Goal drafting

**Question/proposal.** The Agent drafts a concise Goal from the confirmed
Maintenance Case, Workspace Objective, or Work Package; the user accepts,
edits, or rejects. Do not ask the user to repeat context in a blank form or put
full graph/history into Goal.

**User response.** “继续”, treated as acceptance by continuation.

**Acceptance.** Refusal or unavailable provider Goal cannot block research.

## 88 — Resume identity

**Question/proposal.** Prefer the original Agent ID/dialog. A compatible runtime
may claim the same identity when the prior runtime is unavailable, while
recording provider/model telemetry and preserving role, permissions, scope, and
history. UI displays status but approvals remain in conversations.

**User response.** Accepted and reiterated that Agent Flow must not waste
tokens.

**Resolution.** One event hash produces at most one Agent wake.

## 89 — Hard token acceptance

**Question/proposal.** Goal persistence, transition, heartbeat, event match,
dedupe, and checkpoint validation consume zero LLM tokens. Wake only when work
exists, with a compact delta packet and pre-reserved budget. One Agent is the
default; reviewers are risk-triggered.

**User response.** “接受”.

**Resolution.** Measure per Goal/node/wake/Agent/reviewer usage and compare
graph-enabled total token cost with a like-for-like baseline. Set thresholds
after measuring rather than guessing.

## 90 — Database hot-path acceptance

**Question/proposal.** Unchanged heartbeat writes nothing. Keep high-frequency
progress/stdout/event streams in memory/SSE/local logs. SQLite persists only
low-frequency authoritative facts and compact state hashes, with bounded SQL
and no N+1.

**User response.** Accepted and again emphasized token efficiency.

**Acceptance.** Record SQL statements, WAL growth, lock waits, and end-to-end
latency; deduplicate concurrent events before one authoritative write.

## 91 — Bounded multi-Agent use

**Question/proposal.** One Research Goal normally resumes one Research Agent.
The deterministic backend may parallelize computations. Split sibling Work
Packages only for distinct objectives, independent judgment, or context
contamination. Reviewers appear only for semantic conflict, backend anomaly,
graph change, or high-risk capability change.

**User response.** Accepted and requested a precise Agent Flow/Active Graph
boundary.

**Resolution.** Process Miner, Graph Curator, and result summarizer are normally
Server Maintenance output modes, not permanently running Agents. Reuse valid
review hashes.

## 92 — Canonical Agent Flow/Graph boundary

**Question/proposal.** Agent Flow owns who/when: identity, role, Goal, Work
Package, checkpoint, watcher, budget, Git, and routing. Factor Research Graph
owns what research evidence permits next: preregistration, semantics,
conditioning, validation, backtest, robustness, audit, and decision. Connect
them only with compact next packets, evidence references, and gap events.

**User response.** “可以”.

**Resolution.** Runtime/provider details and backend implementation workflows
must not enter research graph semantics.

## 93 — One initial graph, two lightweight workflows

**Question/proposal.** Build only the factor-research Active Graph initially.
Planning uses Objective/index/Work Package state; Maintenance uses deterministic
`gap → proposal → approval → implementation → validation → release →
resume/rollback`. Graph those workflows later only if stable semantic branching
emerges.

**User response.** Accepted, required the future graph possibility to be
recorded, and asked whether user authority over research priority explains why
Planning is not yet a graph.

**Resolution.** User authority is one reason; insufficient stable, repeated
planning semantics is another. Question 94 defines the authority boundary.
